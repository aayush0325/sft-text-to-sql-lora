# Results — text-to-SQL LoRA sweep

## Experiment

- **Dataset:** `gretelai/synthetic_text_to_sql` (100k train / 5,851 test rows).
- **Base model:** `unsloth/Llama-3.2-1B-Instruct` (public mirror, no gated license).
- **Hardware:** one Modal **L4** (24 GB, native BF16), ~$0.80/hr.
- **Training:** one epoch, effective batch size 16, AdamW (fused, β = 0.9/0.95,
  wd 0.01), 3% linear warmup then cosine decay, lr 2e-4, max length 1024.
- **Speed settings:** BF16, SDPA/FlashAttention kernels, padding-free batches,
  no activation checkpointing, 8 train / 16 eval per device.
- **Five LoRA configs** from `configs/lora.yaml`, trained sequentially on the
  same data and optimizer schedule.

**Nominal best on this small eval: `mlp_r32`** — 84.4% execution accuracy
(27 / 32) versus 50% for the base model, and the lowest eval loss (0.1890).
Its adapter is copied to `results/runs/best_adapter` and published to Hugging
Face as [`aayush0325/llama-3.2-1b-text2sql-lora-r32`](https://huggingface.co/aayush0325/llama-3.2-1b-text2sql-lora-r32).

**This small eval has been superseded by the 2,000-row paired evaluation below,**
which shows that `mlp_r32`'s lead over the other tuned adapters is not
statistically significant. The table above is kept for the training-loss and
config-level comparison.

## What the metrics mean

- **Final train loss** — next-token cross-entropy on the completion (SQL) tokens
  of the training split at the last optimizer step. Lower is better.
- **Eval loss** — the same loss computed on a held-out slice of the test split
  (500 rows), with labels masked on the prompt. Lower is better.
- **Valid SQL rate** — fraction of generated completions that parse and execute
  successfully against the in-memory SQLite database. The rest are syntax or
  schema errors.
- **Execution accuracy** — fraction of generated SQL queries that both execute
  **and** return exactly the same rows as the reference query. This is the
  metric that matters for text-to-SQL: a low loss does not guarantee correct
  SQL, and a syntactically valid query can still return the wrong rows.

The original SQLite eval used only the 32 hand-curated rows in
`data/eval_set.jsonl`; one query changed accuracy by ~3.1 points. Those numbers
are kept above for continuity but superseded by the larger paired eval below.

## Large paired evaluation (2,000 rows)

To make the comparison rigorous, a deterministic 2,000-row eval set was sampled
from the dataset's test split (`data/eval_set_2000.jsonl`, generated by
`scripts/make_eval_set.py`), deduplicated and filtered to rows whose reference
SQL executes in SQLite. The original 32 rows are included as a fixed subset.
The **same rows** were used for the base model and all five adapters, so
per-row correctness can be compared directly. 1,998 rows were usable after the
eval-time executable-SQL filter.

Reproduce with:

```bash
uv run python scripts/make_eval_set.py --n 2000 --seed 42
uv run python scripts/compare_eval.py --dir results/runs/large_eval --best mlp_r32
```

| model | exec accuracy | Wilson 95% CI | valid SQL | McNemar p vs best | Δ accuracy vs `mlp_r32` (bootstrap 95% CI) |
| --- | --- | --- | --- | --- | --- |
| base | 0.5390 | [0.5171, 0.5608] | 0.8669 | 2.8e-98 | −0.2442 [−0.2663, −0.2222] |
| attn_r8 | 0.7497 | [0.7303, 0.7683] | 0.9294 | 5.2e-07 | −0.0335 [−0.0465, −0.0200] |
| attn_mlp_r16 | 0.7768 | [0.7580, 0.7945] | 0.9464 | 0.228 | −0.0065 [−0.0160, +0.0035] |
| **mlp_r32** | **0.7833** | [0.7647, 0.8008] | **0.9565** | – | – |
| attn_r64_rslora | 0.7758 | [0.7570, 0.7935] | 0.9510 | 0.214 | −0.0075 [−0.0185, +0.0035] |
| all_linear_r16_dora | 0.7808 | [0.7621, 0.7984] | 0.9525 | 0.682 | −0.0025 [−0.0120, +0.0070] |

- **Wilson 95% CI** — interval for each model's accuracy; at n≈2,000 the
  half-width is about ±1.8 points.
- **McNemar exact p** — paired test against `mlp_r32`, using only the rows where
  the two models disagree. Small p means a real difference.
- **Bootstrap 95% CI** — resampling-based interval for the paired accuracy
  difference; an interval containing 0 means no reliable difference.

**Conclusion after the larger eval:** `mlp_r32` is still nominally best and has
the highest valid-SQL rate, but it is **statistically indistinguishable** from
`attn_mlp_r16`, `attn_r64_rslora` and `all_linear_r16_dora` (p = 0.23, 0.21 and
0.68; all bootstrap CIs cross 0). Only the base model and the tiny `attn_r8`
adapter are significantly worse. The earlier 32-row claim that `mlp_r32`
clearly beat the middle configs was a small-sample artifact. The robust finding
is that **any of the larger adapters works about equally well and all are far
better than no fine-tuning**; choosing among the top four should be based on
cost/speed rather than the ~1-point accuracy differences. `mlp_r32` remains the
published model because it was best on both evals and on training/eval loss.

Full per-row predictions are in `results/runs/large_eval/eval_details_2000/`;
machine-readable stats in `results/runs/large_eval/comparison.json` and the
table in `comparison.md`.

```
├── best_adapter/               copy of the mlp_r32 adapter
├── best.json, results.json, results.csv, results.md
├── sqlite_eval.json
└── loss_curves.png
```

Each `adapter/` contains `adapter_model.safetensors`, `adapter_config.json`
and `README.md`. `history.json` holds per-step loss and learning-rate points.
`results/` is gitignored — the binaries stay on disk but are not tracked.

The Modal apps and the `sft-text-to-sql-cache` Volume were deleted after the
download; these files are the only remaining copy of the artifacts.

## How to reproduce

Settings live in `configs/train.yaml` and `configs/lora.yaml`; the app and its
`@app.function` definitions live in `modal_app.py`. To rerun from scratch:

```bash
modal deploy modal_app.py                          # deploy the app once
modal run modal_app.py::smoke_test                 # optional 2-step check
python - <<'PY'
import modal
fn = modal.Function.from_name("sft-text-to-sql-l4", "train_eval_report")
call = fn.spawn()                                  # fire-and-forget, survives local restarts
print(call.object_id, call.get_dashboard_url())
PY
```

Then follow logs with `modal app logs sft-text-to-sql-l4 -f`. When the function
finishes it commits `/cache/runs` to the Volume; download with:

```bash
mkdir -p results && modal volume get <volume> /runs results
```

The sweep is restart-idempotent: a config with a saved adapter is skipped on a
rerun. Change `GPU` in `modal_app.py` and `dtype`/flags in `configs/train.yaml`
to try different hardware or precision.
